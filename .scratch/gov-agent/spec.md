## Problem Statement

토스트 애니메이션 스튜디오 대표는 나라장터와 정부 지원사업 사이트를 직접 열어 공고를 확인합니다. 확인 빈도가 불규칙해서 새 공고를 늦게 알거나 놓치고, 공고를 찾은 뒤에도 공고문과 과업지시서를 읽으며 참가자격을 회사 상황과 직접 대조해야 합니다. 연초 지원사업은 공고를 늦게 알면 사업기획서를 쓸 기간을 잃습니다. 공공 입찰 밖의 민간 외주 일거리(CGLink 외주발주 게시판)도 직접 들어가 봐야 해서, 올라온 글을 늦게 알거나 놓칩니다.

## Solution

매일 정해진 시각에 공공데이터포털의 공식 API 3종(입찰공고, 한콘진 지원사업 공고, 중소기업 지원사업 공고)을 직접 호출하고 CGLink 외주발주 게시판의 공개 RSS를 받아, 새 공고와 지원사업 공고, 민간 외주 글을 증분으로 모읍니다. 대표가 정한 조건으로 거르고, 겹치는 지원사업을 합친 결과를 날짜별 JSON 파일 하나로 내놓습니다. 대표가 공고 하나를 고르면 첨부 문서를 읽어 참가자격을 추출하고 회사 프로필과 대조해 충족, 미충족, 확인필요로 분류하며 근거 문장을 함께 보여 줍니다. 한 소스가 실패해도 나머지 결과는 반드시 도착합니다. 이 결과를 합쳐 보여 주는 일은 daily-report가 맡습니다.

## User Stories

1. 대표로서, 애니메이션, 콘텐츠, 홍보영상, 실감미디어 용역 입찰공고가 매일 정리되어 도착하기를 원합니다. 그래야 사이트를 직접 검색하지 않아도 새 공고를 놓치지 않습니다.
2. 대표로서, 업무구분이 용역인 공고만 보기를 원합니다. 그래야 물품과 공사 공고에 시간을 쓰지 않습니다.
3. 대표로서, 아직 보고서에서 보지 않은 공고만 받기를 원합니다. 그래야 어제 본 공고를 또 보지 않습니다(이야기 43에서 구체화).
4. 대표로서, 같은 공고가 두 번 나오지 않기를 원합니다. 그래야 목록이 짧고 정확합니다.
5. 대표로서, 각 공고에서 공고번호, 공고명, 공고기관, 추정가격, 마감일, 원문 링크를 보기를 원합니다. 그래야 열어 보기 전에 규모와 기한을 압니다.
6. 대표로서, 공고가 어떤 키워드 때문에 걸러져 들어왔는지 보기를 원합니다. 그래야 왜 이 공고가 왔는지 납득합니다.
7. 대표로서, 관련 없는 공고가 줄어들도록 포함 키워드와 제외 키워드를 정하기를 원합니다. 그래야 보고서가 길어지지 않습니다.
8. 대표로서, 추정가격 범위와 기관 유형으로도 거르기를 원합니다. 그래야 우리 규모에 맞지 않는 공고를 제외합니다.
9. 대표로서, 마감까지 남은 일수를 조건으로 쓰기를 원합니다. 그래야 이미 준비하기 늦은 공고를 따로 봅니다.
10. 대표로서, 공고명이 부분만 일치해서 섞여 들어온 공고를 한 번 더 걸러 주기를 원합니다. 그래야 엉뚱한 공고가 보이지 않습니다.
11. 대표로서, CGLink 외주발주 게시판에 새 외주 글이 올라왔는지 매일 알기를 원합니다. 그래야 공공 입찰 말고도 민간 일감을 놓치지 않습니다. (2026-11-09: 이전의 경쟁사 낙찰 이야기는 요구사항이 아니어서 뺐습니다)
12. 대표로서, 외주 글의 제목, 등록일, 작성자, 원문 링크를 보기를 원합니다. 그래야 원문을 열어 볼지 바로 정합니다.
13. 대표로서, 외주 글은 거르지 않고 새 글을 모두 보기를 원합니다. 한 달에 몇 건뿐이라 키워드로 거르면 오히려 놓칩니다.
14. 대표로서, 연초 애니메이션 지원사업 공고를 게시 직후에 받기를 원합니다. 그래야 사업기획서를 쓸 기간을 확보합니다.
15. 대표로서, 지원사업 공고의 제목, 분류, 등록일, 접수 시작일과 마감일, 원문 링크를 보기를 원합니다. 그래야 신청 여부를 빨리 판단합니다.
16. 대표로서, 지원사업 마감까지 남은 일수(D-day)를 보기를 원합니다. 그래야 급한 것부터 봅니다.
17. 대표로서, 한콘진과 중소기업 지원사업 공고에 같은 사업이 있어도 한 번만 보기를 원합니다. 그래야 중복으로 헷갈리지 않습니다.
18. 대표로서, 합쳐진 사업에서 어느 출처에서 왔는지도 보기를 원합니다. 그래야 원문을 어디서 확인할지 압니다.
19. 대표로서, 지원사업은 애니메이션과 콘텐츠 제작 관련 키워드로 걸러지기를 원합니다. 그래야 무관한 사업이 섞이지 않습니다.
20. 대표로서, 공고 하나를 골라 우리 회사가 참여할 수 있는지 근거와 함께 알기를 원합니다. 그래야 공고문을 처음부터 읽지 않아도 판단합니다.
21. 대표로서, 공고의 첨부 문서(공고문, 과업지시서, 제안요청서)가 자동으로 읽히기를 원합니다. 그래야 문서를 내려받아 열어 보지 않아도 됩니다.
22. 대표로서, 읽지 못한 첨부는 '읽지 못함'과 원문 링크로 표시되기를 원합니다. 그래야 빠진 내용이 있다는 것을 압니다.
23. 대표로서, 참가자격, 계약 방식, 평가 방식, 예산, 제출 마감이 추출되기를 원합니다. 그래야 핵심 조건을 한 곳에서 봅니다.
24. 대표로서, 각 요건이 충족, 미충족, 확인필요 중 하나로 분류되기를 원합니다. 그래야 부족한 부분을 바로 압니다.
25. 대표로서, 판정마다 공고문의 근거 문장과 위치를 보기를 원합니다. 그래야 판정을 믿어도 되는지 확인합니다.
26. 대표로서, 확인하지 못한 요건이 충족으로 표시되지 않기를 원합니다. 그래야 불가능한 공고에 시간을 쓰지 않습니다.
27. 대표로서, 종합 의견이 참여 권고, 조건부, 비권고 중 하나와 이유로 나오기를 원합니다. 그래야 결정을 빨리 내립니다.
28. 대표로서, 종합 의견에 최종 판단은 대표가 한다는 문구가 있기를 원합니다. 그래야 에이전트 의견을 보증으로 오해하지 않습니다.
29. 대표로서, 회사 프로필이 아직 없을 때는 요건만 추출해서 보기를 원합니다. 그래야 프로필이 늦어도 일부 효용이 있습니다.
30. 관리자로서, 입찰공고 필터, 지원사업 검색 조건, 회사 프로필을 설정 md 파일에서 직접 고치기를 원합니다. 그래야 개발자 없이 조건을 바꿉니다.
31. 관리자로서, 설정을 잘못 고쳤을 때 직전 정상 설정으로 실행되기를 원합니다. 그래야 설정 실수로 보고가 끊기지 않습니다.
32. 관리자로서, 설정을 바꾸면 같은 파일 안의 변경 이력에 날짜, 변경 전, 변경 후, 사유, 변경자가 남기를 원합니다. 그래야 언제 무엇을 바꿨는지 압니다.
33. 관리자로서, 소스 하나가 실패해도 나머지 소스는 계속 수집되기를 원합니다. 그래야 한 곳의 장애가 전체를 막지 않습니다.
34. 관리자로서, 실패한 소스와 사유가 결과에 남기를 원합니다. 그래야 키 만료, 승인 상태, 한도 초과 중 무엇이 문제인지 점검합니다.
35. 관리자로서, API 호출 횟수가 일일 한도에 가까워지면 알려 주기를 원합니다. 그래야 누락 없이 운영합니다.
36. 관리자로서, 인증키가 결과 파일과 로그에 남지 않기를 원합니다. 그래야 키가 새지 않습니다.
37. 관리자로서, 마지막 정상 수집 시각이 결과에 남기를 원합니다. 그래야 증분 수집의 기준이 틀어지지 않았는지 확인합니다.
38. 코드프레소 개발자로서, 결과 파일의 형식이 안정적으로 정해져 있기를 원합니다. 그래야 daily-report와 서로 모르고 개발합니다.
39. 코드프레소 개발자로서, 실제 API 응답을 고정해 둔 시험 자료로 수집 전체를 검증하기를 원합니다. 그래야 승인 대기나 한도와 무관하게 시험합니다.
40. 관리자로서, 설정을 바꾼 뒤 다음 보고서에서 그 변경이 결과에 준 영향을 보기를 원합니다. 그래야 틀렸을 때 바로 되돌립니다.
41. 관리자로서, 설정을 되돌릴 때 이전 값을 다시 반영하고 그 사실도 변경 이력에 남기를 원합니다. 그래야 되돌린 흔적까지 추적합니다.
42. 관리자로서, 변경 이력 영역이 설정 값으로 읽히지 않기를 원합니다. 그래야 이력을 적다가 실행이 달라지지 않습니다.
43. 대표로서, 어제까지 보고서에서 본 항목이 오늘 보고서에 다시 나오지 않기를 원합니다. 내용이 조금 바뀐 정정 공고도 본문에 다시 나오지 않아야 합니다. 그래야 매일 처음 보는 것만 확인합니다.
44. 대표로서, 게시에 실패해서 실제로 보지 못한 항목은 다음 보고서에 신규로 나오기를 원합니다. 그래야 수집된 공고를 한 번도 못 본 채 놓치지 않습니다.
45. 대표로서, 보고서에서 빠진 지난 항목을 Google Sheet에서 다시 찾아보기를 원합니다. 그래야 며칠 전 본 공고의 마감일과 원문을 다시 확인합니다.
46. 대표로서, 시트에 내 메모를 적어도 다음 실행이 그 메모를 지우지 않기를 원합니다. 그래야 시트를 검토 기록으로 씁니다.
47. 관리자로서, 시트 기록이 실패해도 보고서는 나오고 실패 사실이 보이기를 원합니다. 그래야 시트 문제로 아침 보고가 끊기지 않습니다.

## Implementation Decisions

**범위와 전제**
- gov-agent는 입찰공고(S1), 한콘진 지원사업(S3), 중소기업 지원사업(S4), CGLink 외주 글(S5)을 수집하고, 제안 가능성 검토를 수행하는 하나의 독립 실행 단위입니다. 실행하면 하루 한 개의 결과 파일을 만듭니다.
- 수집은 공식 API 직접 호출이 기본입니다(상위 PRD V1.3). 개인이 만든 MCP는 수집에 쓰지 않으며, 첨부 변환 같은 보조 기능에서만 선택적으로 검토합니다.
- 사전규격은 수집하지 않습니다. 계약과정통합공개서비스는 번호 하나로 단건 조회하는 구조이므로 일일 수집에 쓰지 않습니다.
- 수집, 중복 제거, 필터, 저장은 결정적인 코드가 맡고, 문서를 읽고 판단하는 일(관련도 2차 판정, 요건 추출, 요건 대조의 판단)만 Claude가 맡습니다. Claude 단계가 실패해도 공고 목록은 결과에 들어갑니다.

**모듈 (책임 단위)**
- **소스 어댑터 4개(S1, S3, S4, S5)**: 소스마다 하나씩 두고 서로 독립으로 실행합니다. 각 어댑터는 호출, 응답 해석, 증분 경계 계산, 오류 분류만 맡습니다.
- **증분 상태 저장소**: 소스별 마지막 정상 수집 시각을 보관합니다. 실패한 날에는 갱신하지 않아서, 다음 실행이 빠진 구간을 다시 받습니다.
- **필터 엔진**: 포함 키워드, 제외 키워드, 추정가격 범위, 마감까지 남은 일수, 기관 유형을 적용하고 일치한 키워드를 항목마다 기록합니다.
- **관련도 판정기**: 부분 일치로 섞인 공고를 Claude로 다시 거르고 한 줄 요약을 붙입니다.
- **CGLink 어댑터(S5)**: 공개 RSS를 하루 한 번 받아 제목, 링크, 작성자, 등록일만 읽습니다. 본문은 연락처가 섞일 수 있어 읽지 않습니다. RSS는 최근 글만 주므로 등록일로 로컬에서 증분을 판정하고, 처음 실행에는 최근 14일치를 보여 줍니다. 필터를 걸지 않습니다.
- (2026-11-09 삭제) 경쟁사 대조기: 낙찰·경쟁사 분석이 요구사항이 아니어서 뺍니다(구현 PRD D15). 낙찰 어댑터, 경쟁사 대조 함수, `settings/competitors.md`, 관련 시험은 2026-11-09에 지웠습니다.
- **지원사업 병합기**: S3과 S4를 한 건으로 합칩니다. 대표 정보는 S4를 쓰고 비어 있는 필드는 S3으로 채우며, 출처는 둘 다 표시합니다(D9).
- **첨부 변환기**: 공고의 첨부 링크를 내려받아 텍스트로 바꿉니다. HWP와 HWPX는 kordoc 스킬로, 그 밖의 파일(PDF, DOCX, PPTX, XLSX 등)은 markitdown으로 읽습니다(D27, 2026-11-09 정함). 실패는 '읽지 못함'으로 남깁니다.
- **요건 추출기와 프로필 대조기**: 참가자격, 계약 방식, 평가 방식, 예산, 제출 마감을 추출하고, 각 요건을 회사 프로필과 대조해 충족, 미충족, 확인필요로 분류합니다. 항목마다 근거 문장과 위치를 인용합니다. 근거를 찾지 못한 요건은 확인필요로 둡니다.
- **결과 작성기**: 하루치 결과를 하나의 JSON 파일로 씁니다.

**결과 파일 계약 (daily-report와 공유, D7)**
- 날짜별 JSON 파일 하나이며, 파일 하나가 에이전트 하나의 하루치입니다.
- 최상위에 실행 메타(실행 일시, 에이전트 이름, 결과 형식 버전)와 소스별 실행 상태(성공 여부, 수집 건수, 실패 사유, 마지막 정상 수집 시각)를 둡니다.
- 항목 목록은 공통 항목(출처, 항목 종류, 항목 식별자, 제목, 등록일, 마감일, 원문 링크, 일치 키워드, 관련도 요약)과 종류별 고유 값(입찰공고의 추정가격과 공고기관, 외주 글의 작성자, 지원사업의 접수 기간과 출처 둘, 제안 가능성 검토 결과)을 구분해서 둡니다.
- 결과 형식에는 버전 값을 두고, 호환이 깨지는 변경은 버전을 올립니다.

**설정 (관리자가 고치는 대상)**
- 설정은 입찰공고 필터, 지원사업 검색 조건, 회사 프로필, 시연 판정 기준 네 가지이며(CONTEXT.md의 용어. 경쟁사 목록은 2026-11-09에 뺌). 직전 정상 설정으로 대신 실행하는 것은 수집용 2종(입찰공고 필터, 지원사업 검색 조건)뿐입니다, 종류마다 md 파일 하나가 정본입니다. 같은 파일 안에 현재 값과 변경 이력을 함께 둡니다(D11).
- 코드는 매 실행을 시작할 때 설정 md를 읽어 값으로 씁니다. 값 영역만 해석하고 변경 이력 영역은 해석하지 않습니다.
- 변경은 별도 승인이나 시험 실행 없이 설정 파일에 바로 반영하고 변경 이력에 한 줄 남기며, 다음 보고서에서 사후 검토합니다. 되돌리기는 이전 값을 다시 반영하는 것입니다.
- 설정 파일에 오류가 있으면 직전 정상 설정으로 실행하고 결과의 실행 메타에 사실을 남깁니다. 직전 정상 설정은 오류 없이 끝난 실행마다 갱신합니다.
- 대화로 값을 바꿀 때 변경 전후를 보여 주고 저장 전에 한 번 확인하는 방식(상위 PRD US-02)은 시험 실행이 아니므로 유지할 수 있습니다. 이 대화 방식은 P1이며 11/11 필수 범위가 아닙니다.
- 변경 위젯은 11/12 이후이고, 위젯이 만든 변경 내용은 Claude 대화에서 설정 md에 반영합니다. 위젯은 설정 파일을 직접 고치지 못합니다(artifact가 로컬 파일을 쓸 수 없음, 2026-11-05 리서치).

**API 계약 (2026-11-04 확인 기준)**
- 공공데이터포털 3종(S1, S3, S4)은 data.go.kr에서 서비스별 활용신청과 승인이 필요하고, 승인 전 호출은 접근 거부 오류가 납니다. S5(CGLink)는 인증 없이 공개 RSS를 받습니다.
- S1: 요청 주소는 입찰공고정보서비스이며, 용역 입찰공고 목록 조회 오퍼레이션이 있습니다. 필수 파라미터는 인증키, 페이지 번호, 페이지당 건수, 조회 구분이며 조회 기간(시작, 종료)과 응답 형식 지정이 선택으로 있습니다. 응답에 첨부 파일 링크 필드가 있습니다.
- S2(낙찰): 2026-11-09에 수집 대상에서 뺐습니다(구현 PRD D15).
- S5(CGLink): `cglink.com/jobsOffer/rss`. 항목마다 제목, 링크, 작성자(dc:creator), 등록일(pubDate)이 있습니다. 2026-11-09에 받은 실제 RSS로 응답 모양을 확인했습니다. 이용약관상 자동 수집 허용 여부는 확인하지 않았습니다(구현 PRD R13).
- S3: 자유공모, 지정공모, 모집공고를 제공하고 제목, 사업번호, 분류, 등록일, 게시글 링크, 접수 시작일과 마감일이 있습니다.
- S4: 등록일자와 수정일시로 증분 조회할 수 있고, 신청기간, 지원대상, 문의처, 첨부 경로가 응답에 있습니다.
- 확인되지 않은 항목은 구현 첫 단계에서 승인된 키로 직접 확인합니다: 영문 오퍼레이션 경로, 조회 구분의 값, 조회 기간의 형식(예시 기준 12자리 일시), 인증키의 인코딩 규칙, 공고명 일치 방식, S3의 요청 주소와 파라미터와 증분 방법, 각 서비스의 일일 한도(서비스별인지 합산인지).
- S3처럼 증분 파라미터가 없으면 전체 목록을 받아 등록일로 로컬에서 증분을 판정합니다.

**호출 한도와 실패 처리**
- 개발계정의 일일 한도는 입찰공고 서비스에서 1,000건으로 표시됩니다. 호출 예산을 소스별로 세고, 한도에 가까워지면 그 소스를 중단하고 '한도 임박'으로 실패 상태에 기록합니다.
- 소스 하나의 실패는 다른 소스에 영향을 주지 않습니다. 오류는 인증 오류, 승인 대기, 한도 초과, 네트워크 오류, 응답 형식 오류로 분류해 사유에 남깁니다.
- 인증키는 환경 설정에서만 읽고, 결과와 로그에 쓰지 않습니다.

**보여 준 항목 제외와 수집 원장 (2026-11-09 추가, 구현 PRD IM-09, D13·D14)**
- 지금 코드와 다른 점: 현재는 `state/state.json`의 `seen`(항목별 내용 지문)을 수집할 때 갱신하고, 내용이 바뀐 항목을 `is_new=false`로 다시 싣습니다. 이 동작을 아래 규칙으로 바꿉니다.
- **수집 원장**: 필터를 통과한 항목마다 한 행을 둡니다. 키는 `소스:항목 식별자`이고, 값은 시트 열과 같습니다(종류, 제목, 기관, 금액, 마감일, 원문 링크, 일치 키워드, 첫 수집일, 최근 변경일, 첫 노출일, 내용 지문). 로컬 파일(`state/` 아래)에 두며 이것이 노출 판정의 정본입니다. 기존 `seen`은 이 원장으로 대체합니다.
- **결과 파일에 싣는 기준**: 첫 노출일이 비어 있는 항목만 결과 파일 `items`에 싣습니다. 수집 시각과 무관하게, 어제 수집했지만 아직 보여 주지 않은 항목도 다시 싣습니다. 이 항목들은 모두 `is_new=true`입니다.
- **바뀐 항목**: 첫 노출일이 있는 항목의 내용 지문이 바뀌면 원장의 최근 변경일만 갱신하고 `items`에는 싣지 않습니다. 소스 상태에 `changed_shown_count`(이미 보여 준 항목 중 오늘 내용이 바뀐 건수)를 더해 daily-report가 상단 한 줄로 알리게 합니다(가정, 구현 PRD Q11). 예외로, 대표가 시트에서 2차 검토를 요청한 공고가 바뀌면 다시 알립니다(구현 PRD D18). 시트의 요청 칸을 원장으로 읽어 오는 방법은 Apps Script 연결(D19)과 함께 정합니다.
- **입찰공고 포함 키워드의 출처**: `settings/company-profile.md`의 주요 사업 분야와 수행 실적에서 뽑아 `settings/bid-filter.md`에 둡니다(구현 PRD D22). 코드가 프로필에서 키워드를 직접 읽지는 않으며, 프로필의 사업 분야가 바뀌면 관리자가 필터 설정도 함께 고칩니다.
- **노출 기록 계약 (daily-report와 공유)**: 보고서 게시에 성공하면 daily-report의 `record-publish --ok true`가 결과 폴더에 `shown_<날짜>.json`(게시한 보고서에 실린 항목 키 목록과 게시 일시)을 씁니다. gov-agent는 실행을 시작할 때 결과 폴더의 `shown_*.json`을 모두 읽어, 첫 노출일이 비어 있는 키에 그 날짜를 채웁니다. 이미 채운 값은 바꾸지 않으므로 같은 파일을 여러 번 읽어도 결과가 같습니다. 원장에 없는 키는 무시합니다.
- **병합 지원사업**: S3·S4를 합친 한 건은 출처 키 둘을 함께 봅니다. 하나라도 첫 노출일이 있으면 보여 준 것으로 보고, 노출 기록은 출처 키 둘 모두에 채웁니다.
- **필터에서 제외된 항목**: 지금처럼 건수만 남기고 원장과 시트에 넣지 않습니다(가정, 구현 PRD Q11). 설정을 바꿔 나중에 통과하게 된 항목은 그때 원장에 처음 들어가므로 신규로 실립니다.
- **Google Sheet 동기화**: 실행 끝에 원장의 행을 시트 '수집 이력'에 키 기준으로 덮어씁니다(없으면 추가). 코드가 쓰는 열만 갱신하고, 코드가 쓰지 않는 '대표 메모' 열은 건드리지 않습니다. 시트 기록 실패는 다른 단계에 영향을 주지 않으며, 결과 파일 최상위의 `sheet`(성공 여부, 실패 사유, 밀린 행 수)에 남기고 다음 실행에서 다시 씁니다. 시트 주소와 접근 비밀값은 `.env`에서만 읽고 결과와 로그에 쓰지 않습니다.
- **시트 쓰는 방식은 미정**입니다(구현 PRD Q10, R9). 정해지기 전에는 동기화 단계를 '설정 안 됨'으로 건너뛰고 나머지는 그대로 동작합니다. 동기화 모듈은 원장 행 목록을 받아 시트에 쓰는 일만 맡는 하나의 경계로 두어, 방식이 정해지면 그 안만 채웁니다.
- **처음 적용하는 날**: 운영 보고서가 아직 게시된 적이 없으므로 기존 `seen`을 노출 기록으로 옮기지 않습니다. 원장을 처음 만드는 실행에서 필터를 통과한 항목은 모두 신규입니다.
- 결과 형식 버전: `is_new`의 뜻이 '오늘 처음 수집'에서 '아직 보여 주지 않음'으로 바뀌고 `changed_shown_count`, `sheet`가 늘어납니다. 필드 이름과 형식은 그대로이고 daily-report는 모르는 필드를 무시하므로 버전은 올리지 않습니다(가정). `docs/result-format.md`는 구현할 때 함께 고칩니다.

**겹치는 지원사업의 판정 기준 (가정, 확인 필요)**
- 정규화한 제목과 접수 마감일이 같으면 같은 사업으로 봅니다. 이 기준은 사용자가 정하지 않았으므로 구현 전에 사용자에게 확인하고, 실제 응답을 본 뒤 조정합니다.

**제안 가능성 검토**
- 입력은 공고 식별자입니다. 입찰공고(S1)만 대상으로 합니다.
- 회사 프로필이 없으면 요건 추출까지만 수행하고 대조는 하지 않습니다(상위 PRD P2). 프로필이 들어오면 같은 공고를 다시 돌려 대조를 켭니다.
- 프로필의 값마다 확인 상태(확인됨, 일부 확인, 추정, 대표 확인 필요)가 있습니다. **확인 상태가 '확인됨'인 값만 충족 판정에 쓰고**, 일부 확인이나 대표 확인 필요인 값에 의존하는 요건은 '확인필요'로 분류합니다. 홈페이지에 자기 기재한 수행 실적처럼 증빙이 없는 값을 충족의 근거로 삼지 않기 위한 규칙입니다(제가 정한 규칙이며 확인이 필요합니다).
- 2026-11-05 시점의 프로필 초안은 직접생산확인, 중소기업·소기업·벤처 확인, 나라장터 등록 업종, 보유 인력이 모두 대표 확인 필요였습니다. 2026-11-09에 등록 업종과 중소기업 확인은 공공 기록(조달데이터허브)으로 '확인됨'이 되었고, 나머지는 '일부 확인'이나 '추정'으로 남아 있습니다. '확인됨'이 아닌 값에 걸린 요건은 계속 '확인필요'로 나옵니다.
- 종합 의견(참여 권고, 조건부, 비권고)에는 최종 판단은 대표가 한다는 문구를 항상 넣습니다. 낙찰 가능성은 점수로 보증하지 않습니다.

**실행 환경**
- 대표 PC에서 로컬로 실행되고, 상위 실행은 daily-report가 소유한 예약 작업이 시작합니다. gov-agent는 예약 작업과 무관하게 단독으로 실행할 수 있어야 합니다.

## Testing Decisions

- 좋은 시험은 외부에서 보이는 동작만 검증합니다. 어댑터와 필터의 내부 함수는 직접 시험하지 않습니다.
- **경계 A (수집 실행)**: 입력은 설정(입찰공고 필터, 지원사업 검색 조건)과 S1, S3, S4, S5의 고정 응답 모음이고, 출력은 결과 JSON입니다. 네트워크 계층만 고정 응답으로 대체합니다. 고정 응답은 승인된 키로 실제 응답을 한 번 받아 키를 지운 뒤 보관하고, 승인 전에는 문서의 응답 예시로 임시 구성합니다.
- 경계 A에서 검증할 동작: 신규와 변경 공고만 수집됨, 중복 제거, 업무구분 용역만 통과, 포함·제외 키워드와 가격 범위 적용, 일치 키워드 기록, CGLink 새 글만 필터 없이 수집되고 본문은 결과에 없음, S3과 S4 병합과 출처 표시, D-day 계산, 한 소스 실패가 다른 소스에 영향을 주지 않음, 실패한 날에는 증분 기준이 갱신되지 않음, 한도 임박 시 중단과 기록, 결과와 로그에 키가 없음, 설정 오류 시 직전 정상 설정으로 실행됨, md에서 바꾼 값이 다음 실행에 반영됨, 변경 이력 영역은 값으로 해석되지 않음.
- 경계 A에서 추가로 검증할 동작(2026-11-09): 노출 기록 파일에 있는 항목은 다음 실행 결과에 나오지 않음, 노출 기록이 없는 어제 수집 항목은 오늘 다시 나옴, 이미 보여 준 항목의 내용이 바뀌면 `items`에 없고 `changed_shown_count`에 세어짐, 병합 지원사업은 출처 하나만 보여 줬어도 다시 나오지 않음, 같은 노출 기록 파일을 두 번 읽어도 첫 노출일이 바뀌지 않음, 시트 기록 실패가 결과 파일 작성과 증분 상태 갱신을 막지 않음, 시트 동기화가 '대표 메모' 열을 보내지 않음, 결과와 로그에 시트 비밀값이 없음. 시트 쪽은 네트워크 계층만 가짜로 대체합니다.
- **경계 B (제안 가능성 검토)**: 입력은 변환된 공고 텍스트와 회사 프로필이고, 출력은 요건별 분류와 근거입니다. Claude 판단 단계만 대체하며, 분류 규칙과 근거 인용의 형식을 검증합니다.
- 경계 B에서 검증할 동작: 근거 문장을 찾지 못한 요건은 확인필요, 프로필이 없으면 대조 없이 추출만, 변환 실패 파일은 '읽지 못함'과 링크, 종합 의견에 대표 판단 문구 포함, 미충족이 하나라도 있으면 참여 권고가 나오지 않음.
- 선행 시험 자료(prior art)는 없습니다. 이 저장소는 새 코드베이스이므로 첫 시험이 이후 시험의 기준이 됩니다.

## Out of Scope

- 사전규격 수집
- CGLink 외의 외주 플랫폼 수집(상위 PRD가 대상에서 제외)
- 낙찰정보 수집과 경쟁사 분석(요구사항이 아님, 구현 PRD D15)
- 시장 정보 에이전트(유튜브 수집, 주간 동향): market-agent의 몫
- 통합 보고서 화면과 artifact 게시, 실행 기록: daily-report의 몫
- 입찰서류와 사업기획서의 자동 작성과 제출
- 낙찰 가능성 점수의 보증
- 대표 외 다수 사용자의 권한 관리
- KMS 적재용 Markdown 출력(상위 PRD US-10, P1)과 변경 위젯, 필터 변경 대화(IM-07, P1)는 11/11 이후
