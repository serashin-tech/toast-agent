## Problem Statement

대표는 나라장터, 지원사업, CGLink 외주 게시판, 시장 동향을 각각 다른 곳에서 확인합니다. 정리된 한 장이 없어서 매번 여러 곳을 열어야 하고, 오늘 먼저 볼 것과 마감이 임박한 것을 직접 가려야 합니다. 에이전트가 모아 준 결과가 있어도, 한 소스가 실패했는데 그 사실이 보이지 않으면 대표는 "오늘은 새 공고가 없다"고 오해할 수 있습니다. 또한 매일 같은 시각에 도착하지 않으면 확인하는 습관이 생기지 않습니다.

## Solution

매일 11:00까지(10:00 시작, D5), 에이전트들이 만든 결과 파일을 합쳐 보고서 한 장을 만들고 artifact로 게시합니다(전달 경로는 맨 위 D28~D30 상자가 우선합니다). 대표는 같은 링크를 데스크톱과 휴대폰 Claude 앱에서 열어 오늘 볼 3건과 마감 임박 건을 먼저 보고, 소스별 절에서 나머지를 확인합니다. 수집에 실패한 소스는 보고서 맨 위에 표시해서 "새 공고 없음"과 "수집 실패"를 구분하게 합니다. 실행마다 결과를 기록해 도착 여부를 날짜별로 셉니다. 보고서에는 API 키를 넣지 않습니다.

## User Stories

1. 대표로서, 매일 11:00까지 보고서 한 장이 도착하기를 원합니다. 그래야 한 번만 열어 보면 됩니다.
2. 대표로서, 같은 링크를 열면 항상 최신 보고서가 보이기를 원합니다. 그래야 링크를 매일 찾지 않습니다.
3. 대표로서, 휴대폰 Claude 앱에서도 같은 보고서를 읽기를 원합니다. 그래야 외출 중에도 확인합니다.
4. 대표로서, 보고서 맨 위에서 오늘 먼저 볼 3건을 보기를 원합니다. 그래야 10분 안에 핵심을 파악합니다.
5. 대표로서, 마감이 임박한 공고와 지원사업을 따로 모아 보기를 원합니다. 그래야 기한을 놓치지 않습니다.
6. 대표로서, 입찰공고, 지원사업, 민간 외주(CGLink)가 소스별 절로 나뉘어 있기를 원합니다. 그래야 찾는 것이 쉽습니다.
7. 대표로서, 상단 외의 나머지 항목은 접혀 있기를 원합니다. 그래야 보고서가 길어도 압도되지 않습니다.
8. 대표로서, 수집에 실패한 소스가 보고서 맨 위에 표시되기를 원합니다. 그래야 "새 공고 없음"을 "수집 실패"와 혼동하지 않습니다.
9. 대표로서, 실패한 소스의 마지막 정상 수집 시각을 보기를 원합니다. 그래야 어디까지 믿어도 되는지 압니다.
10. 대표로서, 모든 항목에서 원문 링크를 누르기를 원합니다. 그래야 바로 원문을 확인합니다.
11. 대표로서, 입찰공고 항목에서 공고명, 기관, 추정가격, 마감일을 보기를 원합니다. 그래야 열어 보기 전에 판단합니다.
12. 대표로서, 민간 외주 항목에서 글 제목, 등록일, 작성자를 보기를 원합니다. 그래야 원문을 열어 볼지 바로 정합니다. (2026-11-09: 이전의 낙찰·경쟁사 항목은 요구사항이 아니어서 뺐습니다)
13. 대표로서, 지원사업 항목에서 접수 기간과 마감 D-day를 보기를 원합니다. 그래야 신청 기한을 압니다.
14. 대표로서, 공고별 제안 가능성 검토 결과(충족, 미충족, 확인필요, 종합 의견)가 보고서에서 이어지기를 원합니다. 그래야 판단 근거를 같은 곳에서 봅니다.
15. 대표로서, 에이전트가 쓴 요약과 원문에서 가져온 문장이 구분되어 보이기를 원합니다. 그래야 요약을 원문으로 착각하지 않습니다.
16. 대표로서, 출처 없는 수치가 보고서에 나오지 않기를 원합니다. 그래야 보고서를 믿습니다.
17. 대표로서, 새 항목이 하나도 없는 날에도 보고서가 도착해서 "오늘은 새 공고가 없습니다"가 분명히 보이기를 원합니다. 그래야 보고서가 안 온 것인지 없는 것인지 헷갈리지 않습니다.
18. 대표로서, 한글이 어절 단위로 줄바꿈되고 휴대폰 화면 폭에서 가로 스크롤 없이 읽히기를 원합니다. 그래야 작은 화면에서도 읽기 편합니다.
19. 대표로서, 보고서가 밝은 화면과 어두운 화면 모두에서 읽히기를 원합니다. 그래야 환경에 상관없이 읽습니다.
20. 관리자로서, 날짜별 실행 기록(시작과 종료 시각, 소스별 성공 여부, 게시 성공 여부, 실패 사유)을 보기를 원합니다. 그래야 문제가 생기면 점검 순서를 정합니다.
21. 관리자로서, 대표 PC가 꺼져 있어서 실행되지 못한 날도 기록에 남기를 원합니다. 그래야 실제 도착률을 정직하게 측정합니다.
22. 관리자로서, 11시 도착률(D5)을 날짜 범위로 계산해 보기를 원합니다. 그래야 11/25에 목표 수치를 정합니다.
23. 관리자로서, 소스 중 하나가 오래 걸려도 정해진 시각에 나머지로 보고서가 나오기를 원합니다. 그래야 한 곳의 지연이 전체를 막지 않습니다.
24. 관리자로서, 게시에 실패하면 다음 실행 전에 알 수 있기를 원합니다. 그래야 다음 날 같은 문제를 반복하지 않습니다.
25. 관리자로서, 보고서와 로그에 API 키와 개인 정보가 없다는 것을 확인하기를 원합니다. 그래야 보고서를 공유해도 안전합니다.
26. 관리자로서, 보고서에 들어가는 소스 목록이 설정으로 정해지기를 원합니다. 그래야 market-agent 같은 새 소스를 코드를 고치지 않고 붙입니다.
27. 코드프레소 개발자로서, 에이전트 결과 파일이 정해진 형식으로 들어온다고 가정하고 보고서를 만들기를 원합니다. 그래야 gov-agent와 서로 모르고 개발합니다.
28. 코드프레소 개발자로서, 고정한 결과 파일만으로 보고서 생성 전체를 검증하기를 원합니다. 그래야 API나 네트워크 없이 시험합니다.
29. 대표로서, 보고서 화면에서 정렬과 마감 임박만 보기, 소스별 접기를 고르기를 원합니다. 그래야 필요한 것만 빠르게 봅니다.
30. 대표로서, 화면에서 고른 보기 방식이 설정을 바꾸거나 저장되지 않기를 원합니다. 그래야 실수로 운영 조건을 건드리지 않습니다.
31. 관리자로서, 최근에 설정이 바뀌었으면 보고서 상단에서 변경 내용과 결과에 준 영향을 보기를 원합니다. 그래야 사후 검토를 보고서에서 바로 합니다.
32. 대표로서, 보고서에는 아직 보지 않은 항목만 나오기를 원합니다. 그래야 어제 검토한 공고를 오늘 다시 읽지 않습니다.
33. 대표로서, 이미 본 공고의 내용이 바뀌었으면 상단 한 줄로 건수만 알고, 자세한 것은 시트에서 확인하기를 원합니다. 그래야 정정 공고를 놓치지 않으면서 보고서가 길어지지 않습니다.
34. 대표로서, 수집 결과를 Google Sheet에 저장하지 못한 날에는 그 사실이 보고서 위에 보이기를 원합니다. 그래야 시트에 오늘 행이 없는 이유를 압니다.

## Implementation Decisions

**범위와 전제**
- daily-report는 에이전트들이 남긴 날짜별 결과 파일을 읽어 보고서 한 장을 만들고, 게시하고, 실행을 기록합니다. 수집과 판단은 하지 않습니다.
- 이번 spec의 입력은 gov-agent의 결과 파일입니다. market-agent의 결과는 같은 계약으로 나중에 붙일 수 있도록 소스 목록을 설정으로 둡니다.
- 루틴은 오전 10:00에 시작합니다(D5, 2026-11-09 정정: 대표 PC가 가장 확실하게 켜져 있는 시각). 보고 마감(시간 상자)은 10:50, 도착 기준은 11:00입니다(같은 날 정함).

**입력 계약 (gov-agent와 공유, D7)**
- 에이전트마다 하루 한 개의 JSON 파일입니다. 최상위에 실행 메타와 소스별 실행 상태(성공 여부, 수집 건수, 실패 사유, 마지막 정상 수집 시각)가 있고, 항목은 공통 항목과 종류별 고유 값으로 구분됩니다.
- daily-report는 결과 형식 버전을 확인하고, 모르는 버전이면 그 에이전트를 '형식 오류'로 실패 처리합니다. 파일이 없거나 읽을 수 없어도 같은 방식으로 실패 처리합니다.
- 오늘 날짜의 파일이 없으면 오늘 결과가 없는 것이며, 어제 파일로 대체하지 않습니다.

**보고서 구성**
- 맨 위: 수집 실패 소스(있을 때), 오늘 볼 3건, 마감 임박 건.
- 그 아래: 소스별 절(입찰공고, 지원사업, 민간 외주(CGLink), 이후 시장 정보). 외주 글은 마감일이 없으므로 오늘 볼 3건과 마감 임박에는 들어가지 않고 자기 절에만 나옵니다. 상단에 올리지 않은 항목은 접어서 표시합니다.
- 새 항목이 없는 소스는 절을 숨기지 않고 "새 항목 없음"을 표시합니다. 수집 실패와는 다른 표시를 씁니다.
- 모든 항목에 원문 링크를 두고, 에이전트가 쓴 요약은 원문 인용과 구분해서 표시합니다.
- 제안 가능성 검토 결과가 있는 공고에는 결과(충족, 미충족, 확인필요, 종합 의견, 근거 문장)를 그 공고 아래에서 펼쳐 볼 수 있게 합니다.
- 최근 7일 안에 설정이 바뀌었으면 보고서 상단에 변경 내용을 한 줄로 보여 주고, 전날 대비 포함·제외 건수 변화를 함께 표시합니다. 사후 검토를 보고서에서 바로 하게 하는 기능이며, 2026-11-05에 포함하기로 정했습니다. 7일이라는 기간은 제안값입니다.

**보여 준 항목 제외 (2026-11-09 추가, 구현 PRD IM-09, D13)**
- 보고서는 결과 파일의 `is_new=true` 항목만 표시합니다. gov-agent가 아직 보여 주지 않은 항목만 싣도록 바뀌므로 보통은 모든 항목이 해당되지만, `is_new=false`가 들어와도 표시하지 않습니다. 지금의 "나머지 N건 보기 (새 항목 M건)"처럼 새 항목과 지난 항목을 섞어 보여 주는 표시는 없앱니다.
- 오늘 볼 3건, 마감 임박, 소스별 절이 모두 이 기준을 따릅니다. 따라서 한 번 보여 준 공고는 마감이 다가와도 마감 임박에 다시 나오지 않습니다(구현 PRD R10, Q12).
- 소스 상태의 `changed_shown_count`가 1 이상이면 보고서 상단에 "이미 보신 공고 N건의 내용이 바뀌었습니다(시트에서 확인)"를 한 줄로 표시합니다. 시트 주소는 보고서에 넣지 않습니다(artifact는 공유될 수 있는 페이지이므로, 시트 주소는 대표가 따로 보관합니다. 가정).
- 결과 파일의 `sheet`가 실패이면 수집 실패 표시와 같은 자리에 "수집 이력 시트에 저장하지 못했습니다(다음 실행에서 다시 씀)"를 표시합니다. 시트 실패는 수집 실패와 다른 문구를 씁니다.
- **노출 기록**: `record-publish --ok true`는 실행 기록을 남길 때 그날 결과 파일에 실린 항목 키(소스와 항목 식별자)를 `shown_<날짜>.json`으로 결과 폴더에 씁니다. 형식은 gov-agent spec의 '노출 기록 계약'을 따릅니다. `--ok false`이면 쓰지 않으므로, 게시에 실패한 날의 항목은 다음 보고서에 다시 나옵니다. 실행 기록에는 노출 기록 건수를 함께 남깁니다.
- 노출 기록은 게시한 보고서에 실제로 실린 항목만 담습니다. 결과 파일이 형식 오류였거나 없어서 보고서에 실리지 않은 에이전트의 항목은 기록하지 않습니다.

**'오늘 볼 3건'과 '마감 임박'의 선정 기준 (가정, 확인 필요)**
- 사용자가 정하지 않은 기준입니다. 제안은 다음과 같고, 구현 전에 사용자에게 확인합니다.
  - 마감 임박: 마감까지 7일 이내인 입찰공고와 지원사업.
  - 오늘 볼 3건: 오늘 새로 들어온 항목 중에서 마감이 가까운 순으로 고르고, 같으면 일치 키워드가 많은 순으로 고릅니다. 새 항목이 3건 미만이면 있는 만큼만 표시합니다.
- 기준은 보고서 안에서 한 줄로 설명해서, 대표가 왜 이 3건인지 알게 합니다.

**게시 방식**
- 스냅샷 방식으로 시작합니다(D8). 매일 HTML을 새로 만들어 같은 artifact 주소에 다시 게시하므로, 대표의 링크는 바뀌지 않습니다. 대표의 '관련 없음' 표시를 저장하는 db 방식은 11/12 이후입니다.
- 게시 도구가 로컬 예약 작업 안에서 무인으로 동작하는지, 같은 주소 재게시가 승인 대기로 멈추지 않는지는 확인되지 않았습니다(구현 PRD R1). 구현 첫 단계에서 시험하고, 실패하면 보고서 파일을 로컬에 먼저 저장하고 게시 실패를 실행 기록에 남깁니다.
- 보고서에는 API 키와 개인 정보를 넣지 않습니다. artifact는 공유 가능한 페이지이므로 보고서 본문에서 키가 될 만한 값을 넣지 않도록 결과 파일에서 읽는 필드를 정해진 목록으로 제한합니다.

**시간 상자 (제안, 확인 필요)**
- 10:50까지 도착한 결과 파일만으로 보고서를 만들어 게시합니다. 늦는 소스는 '시간 초과'로 실패 처리하고 보고서 상단에 표시합니다. 이 시각은 D5(2026-11-09 정함)를 따르며, 소스별 제한 시간을 따로 정하지는 않았습니다.

**실행 기록**
- 실행마다 날짜, 시작과 종료 시각, 소스별 성공 여부와 사유, 게시 성공 여부, 게시 지연 여부를 한 줄로 기록합니다.
- 11시 도착은 "11:00까지 게시에 성공한 날"로 정의합니다(D5, 이전 기준 10:00). 실행되지 못한 날(PC 꺼짐)은 기록이 없으므로, 날짜별로 기록이 없는 날을 '미실행'으로 세어 도착률 분모에 넣습니다.
- 도착률의 목표 수치는 11/25에 정하며, 이 spec은 계산 방식만 정합니다.

**화면 규칙**
- 한글이 포함된 HTML이므로 구현할 때 먼저 코드프레소 브랜드 가이드 스킬(codepresso:brand-guide)을 호출해서, 한글 줄바꿈(어절 단위), 읽기 폭, 글꼴 규칙을 적용합니다. 회사 명의 문서가 아니므로 로고와 브랜드 색은 쓰지 않습니다.
- 휴대폰 폭에서 가로 스크롤이 없고, 어두운 화면에서도 읽히며, 접기와 펼치기는 키보드와 터치 모두로 조작할 수 있어야 합니다.
- **보기 위젯**(정렬, 마감 임박만 보기, 소스별 접기)은 11/11에 포함합니다(D12). 화면 안에서만 바뀌고 아무것도 저장하지 않으며, 값 저장이나 파일 다운로드 같은 artifact 런타임 기능을 선언하지 않습니다. 이 기능을 선언한 페이지는 게시 때 승인 프롬프트가 뜰 가능성이 높아서 오전 10시 무인 게시를 막을 수 있기 때문입니다(2026-11-05 리서치).
- 설정을 바꾸는 **변경 위젯**은 매일 게시하는 보고서에 넣지 않습니다. 11/12 이후에 별도 설정 페이지로 분리하는 구조를 검토합니다.

**실행 환경**
- 대표 PC에서 로컬로 실행되며, Cowork 예약 작업이 10:00에 시작합니다(D3, D5). PC가 꺼져 있거나 앱이 실행 중이 아니면 그날은 실행되지 않습니다.

## Testing Decisions

- 좋은 시험은 외부에서 보이는 결과만 검증합니다. 보고서의 내부 조립 함수를 직접 시험하지 않습니다.
- **경계 C (보고서 생성)**: 입력은 고정한 결과 파일들(성공 소스와 실패 소스를 섞은 것)이고, 출력은 HTML 한 장과 실행 기록 한 줄입니다. 네트워크와 게시는 시험하지 않으며, 게시는 마지막 단계의 호출만 가짜로 대체합니다.
- 경계 C에서 검증할 동작: 맨 위에 실패 소스 표시, 마감 임박과 오늘 볼 3건 선정 규칙, 새 항목 없음과 수집 실패의 표시 구분, 소스별 절 구성, 모든 항목의 원문 링크, 요약과 원문 인용의 구분 표시, 제안 가능성 검토 결과 표시, 결과 파일이 없을 때와 형식 버전이 다를 때의 실패 처리, 어제 파일로 대체하지 않음, 보고서에 키 형태의 문자열이 없음, 실행 기록의 필드, 미실행 날짜가 도착률 분모에 들어감.
- 경계 C에서 추가로 검증할 동작(2026-11-09): `is_new=false` 항목이 어느 절에도 나오지 않음, `changed_shown_count` 합계가 상단 한 줄에 나오고 0이면 나오지 않음, 시트 실패 문구가 수집 실패 문구와 다름, `record-publish --ok true`가 실린 항목 키로 `shown_<날짜>.json`을 씀, `--ok false`와 결과 파일이 없는 에이전트는 노출 기록을 남기지 않음, 보고서에 시트 주소가 없음.
- 화면 확인은 자동 시험과 별개로 휴대폰 폭과 어두운 화면에서 한 번씩 눈으로 확인합니다. 이 확인은 11/11 공유 전에 수행합니다.
- 선행 시험 자료(prior art)는 없습니다. gov-agent의 결과 파일 고정 자료를 그대로 재사용해서 두 폴더의 시험이 같은 계약을 가리키게 합니다.

## Out of Scope

- 수집과 판단(gov-agent, market-agent의 몫)
- 시장 정보 에이전트의 결과 표시: 이번에는 소스를 붙일 수 있는 구조까지만 두고, 표시 상세는 market-agent spec에서 정합니다
- 대표의 '관련 없음' 표시 저장과 필터 개선(db 방식, 11/12 이후)
- 변경 위젯(설정 값을 바꾸는 입력, 11/12 이후)
- KMS 적재용 Markdown 출력(상위 PRD US-10, P1)
- 대표 외 다수 사용자 권한 관리와 로그인 화면
- 08:00 전달(10:00으로 변경됨)과 서버 cron 이전 안내(11/25 회차)

## Further Notes

- 이 spec은 구현 PRD의 미확인 항목에 의존합니다: 로컬 예약 작업이 폴더를 연결해 스크립트를 실행하고 artifact를 같은 주소에 재게시할 수 있는지(R1), 네트워크 송신 제한(R7)입니다. 11/5의 Cowork 시험 1~4 결과가 나오기 전에는 게시 단계를 확정하지 않습니다.
- 위에서 '가정'이나 '제안'이라고 표시한 항목(오늘 볼 3건의 선정 기준, 마감 임박의 7일 기준, 최근 설정 변경 표시의 7일 기간)은 사용자가 정한 것이 아니므로 구현 전에 확인합니다.
- 구현 일정은 11/10(통합 보고서와 artifact, 시험 실행), 11/11 공유입니다.
