## Problem Statement

토스트 애니메이션 스튜디오 대표는 나라장터 용역 공고 중 참여할 공고를 고른 뒤, 제안서에 넣거나 발표 때 보여 줄 시안(캐릭터, 화면)을 처음부터 손으로 만듭니다. 시안 제작에는 며칠이 걸리므로, 참여할지 확신이 없는 공고에는 시안을 만들지 못하고, 참여를 늦게 결정하면 시안의 완성도가 떨어집니다. 공고를 찾는 일(gov-agent)과 참가자격을 대조하는 일(제안 가능성 검토)은 이미 구현되어 있지만, 그 결과가 "이 공고에 어떤 시안이 필요한가"로 이어지지 않고, 시안의 첫 초안을 만드는 일도 사람이 처음부터 해야 합니다.

## Solution

공고 하나가 아래 다섯 단계를 차례로 지나갑니다. 앞 단계를 통과한 공고만 다음 단계로 넘어갑니다.

| 단계 | 이름 | 하는 일 | 맡는 쪽 | 상태 |
|---|---|---|---|---|
| 0 | 수집 | 나라장터 용역 공고, 지원사업 공고, CGLink 민간 외주 글을 매일 수집(경쟁사 낙찰은 요구사항이 아니어서 2026-11-09에 뺌, 구현 PRD D15). 결과는 Google Sheet에 저장하고, 보고서에는 아직 보여 주지 않은 항목만 싣는다(구현 PRD IM-09, 2026-11-09 추가) | gov-agent `run`(코드) | 수집은 구현됨(가짜 응답으로 시험). 보여 준 항목 제외와 시트 저장은 명세만 있음 |
| 1 | 1차 검토(검색 조건) | 포함·제외 키워드, 추정가격, 남은 일수, 기관 유형으로 거름 | gov-agent 필터(코드), `settings/bid-filter.md` | 구현됨 |
| 2 | 제안 조건 검토 | 첨부를 읽어 참가자격을 추출하고 회사 프로필과 대조해 권고·조건부·비권고로 분류 | Claude(요건 추출) + gov-agent `eligibility`(대조) | 구현됨 |
| 3 | 2차 검토(시연 판정) | 과업 범위와 평가항목을 읽어 시연·시안이 필요한지 판정하고, 필요하면 **시연 브리프**를 씀 | Claude | **신규** |
| 4 | 1차 시연 데모 제작 | 시연 브리프대로 Adobe for creativity 커넥터를 써서 데모 캐릭터나 데모 화면의 첫 초안을 만듦 | Claude 세션 + Adobe 커넥터 | **신규** |

프로젝트 계획서의 "1단계"는 0~2단계(시안을 만들 공고를 고르는 데까지)입니다. 이번 요청은 그 뒤에 3~4단계를 붙이는 일입니다. 1단계 범위만 계약 과업인지, 3~4단계도 이번 과업에 포함되는지는 열린 질문 Q1입니다.

## User Stories

1. 대표로서, 제안 조건 검토에서 권고나 조건부가 나온 공고만 2차 검토로 넘어가기를 원합니다. 그래야 참여하지 않을 공고에 시안을 만들지 않습니다.
2. 대표로서, 공고가 시연, 시안 제출, 샘플 영상, 캐릭터 디자인 제안을 요구하는지 근거 문장과 위치와 함께 알기를 원합니다. 그래야 제안요청서를 다시 읽지 않아도 시안 필요 여부를 압니다.
3. 대표로서, 시연이 필요한 공고마다 무엇을 만들어야 하는지(캐릭터인지 화면인지, 분량, 규격, 제출 형식, 마감)를 한 장의 시연 브리프로 받기를 원합니다. 그래야 바로 제작을 지시합니다.
4. 대표로서, 평가항목 중 시안이 점수에 영향을 주는 항목과 배점을 시연 브리프에서 보기를 원합니다. 그래야 시안에 들일 노력을 정합니다.
5. 대표로서, 시연 브리프를 확인한 뒤 내가 요청할 때만 데모 제작이 시작되기를 원합니다. 그래야 생성 비용과 시간을 필요한 공고에만 씁니다.
6. 대표로서, 데모 캐릭터나 데모 화면의 첫 초안을 2~4개 안으로 받기를 원합니다. 그래야 방향을 고르고 디자이너에게 넘깁니다.
7. 대표로서, 데모 결과물이 공고번호별 폴더에 시연 브리프, 생성에 쓴 지시문, 결과 파일이나 Adobe 링크와 함께 남기를 원합니다. 그래야 나중에 어떤 조건으로 만든 시안인지 추적합니다.
8. 대표로서, 데모 초안에 "AI가 만든 1차 초안이며 제출 전 디자이너 검수가 필요함"이 표시되기를 원합니다. 그래야 초안을 완성본으로 착각하지 않습니다.
9. 관리자로서, 시연 판정에 쓰는 신호 단어(시연, 시안, 샘플, 데모, 시제품 등)를 설정 파일에서 고치기를 원합니다. 그래야 개발자 없이 판정 기준을 바꿉니다.
10. 관리자로서, 2차 검토나 데모 제작이 실패해도 0~2단계 결과와 보고서가 그대로 도착하기를 원합니다. 그래야 새 단계가 기존 운영을 막지 않습니다.

## 제안 결정 (11/12 확인 필요)

아래는 제가 정한 가정입니다. 회의에서 확인받기 전에는 구현하지 않습니다.

**P1. 데모 제작(4단계)은 코드가 아니라 Claude 세션에서 합니다.**
Adobe for creativity는 Claude 앱의 커넥터 목록에서 연결하는 MCP 커넥터입니다. Python 코드에서 직접 부르는 API가 아니므로, gov-agent에 Adobe 호출 코드를 넣지 않습니다. 대표가 Claude 데스크톱(또는 Cowork)에서 공고번호를 주고 데모를 요청하면, Claude가 시연 브리프를 읽고 커넥터 도구를 부릅니다. 코드에서 직접 호출이 꼭 필요하면 Adobe Firefly Services API(별도 계약)가 대안이지만 이번 범위에서는 제외합니다.

> 2026-11-09 갱신(구현 PRD D16~D24): 3단계(2차 검토)는 대표가 Google Sheet에서 '2차 검토 요청'을 체크하면 **바로 이어서** 처리하고, 결과를 별도 메일로 곧바로 보냅니다(업무 시간 09~18시에 30분마다 시트의 새 요청을 확인, 구현 PRD D25. 상태 칸 값은 D26). 2차 검토는 참가자격 대조와 시연 판정을 함께 하며 입찰공고만 대상입니다. 4단계(데모 생성)는 대표가 시트에서 '데모 확인'을 체크한 뒤 Claude 데스크톱에 한 줄로 요청하면 `DEMO.md`대로 만듭니다(D23). 기록의 정본은 시트 상태 칸과 `drafts/<공고번호>/`입니다(D24). 아래 P2는 4단계에만 남습니다.

**P2. (4단계만 해당) 데모 생성은 매일 10:00 무인 루틴에서 자동으로 돌리지 않습니다.**
현재 `ROUTINE.md`는 제안 가능성 검토도 자동으로 하지 않습니다. 시연 판정은 첨부 전체를 읽어야 해서 시간이 들고, 데모 생성은 Adobe 계정 로그인과 생성량 한도를 쓰며, 결과는 사람이 골라야 합니다. 따라서 대표가 보고서에서 공고를 고른 뒤 요청할 때 실행합니다. 무인 실행은 운영해 본 뒤 다시 정합니다.

**P3. 2차 검토의 결과는 공고번호별 시연 브리프 JSON 하나입니다.**
제안 가능성 검토 결과(`eligibility[]`)와 같은 원칙을 씁니다: 판정마다 근거 문장(`quote`)과 위치(`location`)가 있어야 하고, 근거가 없으면 `needs_check`입니다. 제안 형식은 아래와 같습니다.

```json
{
  "bid_id": "R26BK001",
  "demo_needed": "yes | no | needs_check",
  "reason": "평가항목 '캐릭터 디자인 제안(20점)'에 시안 제출을 요구함",
  "deliverable": "character | screen | both | none",
  "requirements": [
    {"text": "캐릭터 시안 2종 이상 제출", "evidence": {"quote": "…", "location": "제안요청서 12쪽 3항"}}
  ],
  "scoring": [{"item": "캐릭터 디자인 제안", "points": 20}],
  "constraints": {"format": "PNG 또는 PDF", "size": null, "count": 2, "due": "2026-12-01"},
  "style_refs": ["회사 프로필의 대표 작품 1"],
  "disclaimer": "AI가 만든 1차 판정이며 최종 판단은 대표가 합니다."
}
```

**P4. 산출물은 `drafts/<공고번호>/`에 모읍니다.**
`brief.json`(시연 브리프), `prompt.md`(커넥터에 준 지시와 도구 호출 요약), 결과 파일 또는 Adobe 링크 목록(`outputs.md`), 대표 검수 메모(`review.md`)를 둡니다. 인증 정보는 이 폴더에 남기지 않습니다.

**P5. 용어 후보**
CONTEXT.md에 넣을 후보입니다. 회의에서 확정되면 `/domain-modeling`으로 반영합니다.
- **1차 검토**: 검색 조건(설정 `bid-filter.md`)으로 공고를 거르는 일.
- **제안 조건 검토**: 참가자격을 회사 프로필과 대조하는 일. 코드의 `eligibility`, 기존 용어 "제안 가능성 검토"와 같은 것으로 봅니다.
- **2차 검토**: 과업 범위와 평가항목을 읽어 시연 필요 여부를 판정하는 일.
- **시연 브리프**: 2차 검토의 결과. 무엇을 어떤 조건으로 만들어야 하는지 적은 한 장.
- **시연 데모**: 시연 브리프로 만든 첫 초안 캐릭터나 화면. 제출본이 아닙니다.

## 확인하지 못한 기술 전제 (11/10~11 시험)

1. 커넥터가 만든 결과물을 로컬 파일로 받을 수 있는지, Adobe 클라우드 링크로만 받는지 확인하지 못했습니다. 링크로만 받으면 P4의 `outputs.md`에 링크를 남깁니다.
2. 커넥터의 도구가 데스크톱 Photoshop·Illustrator의 전체 기능인지, Express·Firefly 수준인지 출처마다 설명이 다릅니다. 캐릭터 턴어라운드처럼 일관성이 필요한 작업이 되는지 직접 시험해야 합니다.
3. Adobe 계정 없이도 쓸 수 있으나 로그인하면 한도와 도구가 늘어난다는 설명은 제3자 기사에만 있습니다.
4. Cowork 예약 작업에서 이 커넥터를 무인으로 부를 수 있는지 모릅니다(P2 때문에 이번에는 필요 없음).
5. 생성물의 상업적 이용과 정부 제안서 제출 조건(생성형 AI 사용 고지 의무 등)은 공고마다 다를 수 있습니다. 2차 검토에서 해당 문구를 함께 추출하는 것을 검토합니다.

시험 순서: Claude 데스크톱에서 커넥터 연결 → 가짜 공고 1건의 시연 브리프로 캐릭터 시안 2안 생성 → 결과 저장 방식 확인 → 소요 시간과 사용량 기록.

| 시연 판정이 틀려 필요한 시안을 놓침 | 제안 점수 손실 | 근거 없는 판정은 `needs_check`로 두고, 대표가 브리프를 확인한 뒤에만 제작 |
