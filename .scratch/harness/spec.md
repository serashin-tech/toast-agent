## Problem Statement

정부사업 에이전트는 코드와 시험은 있지만, 에이전트가 매일 같은 방식으로 일하게 만드는 장치가 없습니다. 무인 루틴의 지침은 사람이 Cowork에 복사해 붙여 넣는 문서(`ROUTINE.md`, `DEMO.md`)이고, 금지 규칙(키 출력 금지, 설정 수정 금지, 권한 선언 금지)도 그 문서 안에만 있어 지켜졌는지 확인할 방법이 없습니다. 결정이 바뀔 때마다 지침 문서가 뒤처져서, 2026-11-09 검토에서는 보고 채널과 실행 시각이 서로 다른 문서가 여덟 곳 나왔습니다. 루틴을 실제로 한 번도 돌리지 않아 실행 기록(`runs/runs.jsonl`)도 없으므로, 고장이 나도 알아챌 피드백이 아직 없습니다. 11월 25일 지원이 끝나면 관리자가 이 시스템을 이어받아야 하는데, 지금 구조로는 무엇이 정본이고 무엇을 고쳐야 하는지 알기 어렵습니다.

## Solution

지침, 규칙, 검사를 Claude 플러그인 하나에 묶고, 코드와 문서를 버전 관리하는 저장소 하나에 모읍니다. 대표 PC의 작업 폴더는 운영 데이터만 담습니다.

- 무인 루틴과 대화형 절차는 플러그인 스킬이 됩니다. Cowork 예약 작업에는 스킬 이름 한 줄만 넣습니다.
- 불변 규칙은 세션을 시작할 때 훅이 대화에 넣고, 설정 파일을 고칠 때는 훅이 변경 이력 줄을 검사합니다.
- 문서에서 판정 규칙을 반복하지 않고, 판정은 코드가 합니다. Claude가 추출한 인용 문장이 원문에 실제로 있는지도 코드가 대조합니다.
- 통합 시험, 결과 계약 시험, 가짜 응답 리허설, 플러그인 구조 검사가 변경마다 돌고, 주간 점검 스킬이 문서와 코드의 어긋남을 찾습니다.

## User Stories

1. 대표로서, 매일 10:00 루틴이 사람이 붙여 넣은 문서가 아니라 설치된 스킬로 돌기를 원합니다. 그래야 지침이 바뀌어도 예약 작업을 다시 만들지 않습니다.
2. 대표로서, 시트에서 2차 검토를 요청하면 업무 시간 30분 안에 결과 메일을 받고, 입찰 현황판에도 상태가 바뀌어 보이기를 원합니다.
3. 대표로서, 데모를 만들 때 "데모 만들어 줘" 한 줄로 정해진 절차가 시작되기를 원합니다.
4. 대표로서, 설정을 말로 바꾸면 변경 전후를 확인한 뒤 바로 반영되고, 변경 이력이 빠짐없이 남기를 원합니다.
5. 관리자로서, 설정 파일을 고치면서 변경 이력 줄을 빠뜨리면 저장이 막히고 무엇을 더 적어야 하는지 안내받기를 원합니다.
6. 관리자로서, 어느 세션에서든 키 비공개와 설정 보호 같은 불변 규칙이 같은 문구로 적용되기를 원합니다.
7. 관리자로서, 주 1회 점검 결과로 문서와 코드가 어긋난 곳, 미확인 가정, 도착률을 받아 보기를 원합니다.
8. 관리자로서, 저장소의 `CLAUDE.md` 한 장에서 시작해 필요한 문서로 찾아 들어가기를 원합니다.
9. 코드프레소 개발자로서, 코드를 바꾸면 한 명령으로 모든 시험이 돌고, gov-agent와 daily-report 사이의 결과 형식이 깨지면 시험이 실패하기를 원합니다.
10. 코드프레소 개발자로서, 실제 키 없이 고정 응답으로 루틴 전체를 한 번 돌려 실행 기록까지 만들어 보기를 원합니다.
11. 코드프레소 개발자로서, 플러그인 구성이 Cowork에 설치할 수 없는 모양이 되면 시험이 먼저 알려 주기를 원합니다.
12. 대표로서, 근거 문장이 원문에 없는 판정이 '충족'이나 '권고'로 나오지 않기를 원합니다.

## Implementation Decisions

**저장소 (H10, H12, H13)**
- `D:\98_MyCode` 아래에 새 git 저장소를 만듭니다. 원격은 토스트 명의의 GitHub 비공개 저장소이고, 코드프레소가 협업자입니다. 저장소 이름은 구축 때 정합니다.
- 저장소 루트가 마켓플레이스이고 `plugin/`이 플러그인입니다(사내 `proposal_agent`와 같은 배치).
- 저장소 루트에는 개발용 `CLAUDE.md`(약 100줄, 목차와 명령), `ARCHITECTURE.md`, `CONTEXT.md`, `docs/`(decisions.md, result-format.md, adr/), `.scratch/`(명세와 이슈), `apps-script/`(시트에 붙일 Apps Script 원본)를 둡니다. 지금 `07_Implementation`에 있는 같은 이름의 문서를 옮깁니다.
- `.env`, 설정 값, 실행 산출물, 고객 첨부는 저장소에 넣지 않습니다. `.gitignore`와 플러그인 구조 검사가 이를 막습니다.

**작업 폴더 (H11, H12)**
- 대표 PC의 `07_Implementation`(Cowork에 연결하는 폴더)은 운영 데이터 폴더가 됩니다: `settings/`(설정 4종, 루트로 옮김), `.env`, `results/`, `reports/`, `runs/`, `state/`, `drafts/`.
- 스크립트는 작업 폴더를 현재 폴더로 받아 동작합니다. 설정·상태·결과·`.env`의 기본 경로는 작업 폴더 기준입니다.
- 지금 코드는 기본 경로를 코드 파일의 위치에서 계산합니다. 그대로 플러그인으로 옮기면 `.env`를 플러그인 폴더에서 찾게 되어, 공공데이터 소스가 모두 인증 실패로 끝납니다. 그래서 코드를 옮기기 전에 기본 경로를 현재 작업 폴더 기준으로 바꾸는 사전 정리를 먼저 합니다.

**플러그인 구성 (H2, H5, H7, H8, H9)**

| 위치 | 내용 |
|---|---|
| `plugin/.claude-plugin/plugin.json` | 이름, 버전(semver). 대표에게 내보낼 변경은 버전을 올립니다 |
| `plugin/hooks/hooks.json` | SessionStart 훅 하나, PreToolUse 훅 하나 |
| `plugin/rules/invariants.md` | 불변 규칙 원본. 세션 시작 훅이 대화에 넣습니다 |
| `plugin/skills/` | daily-routine, review-requests, make-demo, change-setting, garden |
| `plugin/agents/` | 추출 에이전트 1개 |

- `bin/` 디렉터리는 두지 않습니다. Cowork는 `bin/`이 있는 플러그인을 설치하지 않습니다.
- 스킬과 에이전트 본문의 경로는 `${CLAUDE_PLUGIN_ROOT}/…`로 적습니다.

**불변 규칙 (`rules/invariants.md`)**
- `.env`를 열거나 내용을 출력하지 않습니다. 키는 코드가 직접 읽습니다.
- 무인 루틴(daily-routine, review-requests)은 `settings/`를 고치지 않습니다. 설정은 change-setting으로만 바꿉니다.
- artifact를 게시할 때 capabilities를 선언하지 않습니다.
- 키, 시트 비밀값, 대표 메일 주소를 메일·시트·현황판·로그·`drafts/`에 쓰지 않습니다.
- 판정에는 원문의 근거 문장과 위치가 있어야 하며, 없으면 확인필요입니다. 종합 의견에는 최종 판단은 대표가 한다는 문구를 넣습니다.
- CGLink 글의 본문은 읽지 않습니다. 대표가 허락하지 않은 회사 자료를 외부 커넥터에 올리지 않습니다.
- 첨부는 hwp·hwpx면 kordoc 스킬, 그 밖이면 markitdown으로 읽습니다(D27).

**훅 (H7)**
- SessionStart: `rules/invariants.md`를 그대로 대화에 넣습니다.
- PreToolUse(Write, Edit): 대상이 작업 폴더의 `settings/*.md`이면, 호출 전 파일 내용과 호출을 적용한 뒤의 내용을 비교합니다. 값 영역(`## 변경 이력` 앞의 표)이 바뀌었는데 변경 이력 표의 줄이 늘지 않았으면 막고, 적어야 할 열(날짜, 변경 전, 변경 후, 사유, 변경자)을 메시지로 알립니다.
- 값 표와 변경 이력 표는 파일 안에서 떨어져 있어서, Edit를 두 번으로 나누면 값을 고치는 첫 호출이 언제나 막힙니다. 그래서 change-setting 스킬은 파일 전체를 한 번에 Write합니다. 막힐 때의 메시지도 "파일 전체를 Write로 다시 쓰라"고 안내합니다.
- Bash(sed, python 등)로 설정을 고치면 이 훅을 거치지 않습니다. 불변 규칙이 설정을 Bash로 고치지 말라고 정하고, 그 이상은 막지 않습니다(알려진 한계).
- `.env` 차단 훅은 두지 않습니다(H7). 키 보호는 불변 규칙과 코드에 기댑니다(R7).

**두 루틴이 겹칠 때 (검토 반영)**
- daily-routine(10:00)과 review-requests(30분 간격)는 10:00과 10:30에 겹칠 수 있습니다. 두 루틴 모두 현황판 재게시, 시트 상태 갱신, 실행 기록 쓰기를 합니다.
- review-requests는 10:00~10:50에는 아무것도 하지 않고 끝냅니다. 추가로, 두 루틴은 작업 폴더의 잠금 파일 하나를 잡은 뒤에만 쓰기를 시작합니다. 잠금이 잡혀 있으면 review-requests는 다음 간격으로 미룹니다.
- 실행 기록 한 줄에 루틴 종류(`daily`, `review`)를 넣습니다. 도착 기록은 그날의 `daily` 줄에만 붙입니다. 지금 코드는 "같은 날짜의 마지막 줄"에 붙이므로 바꿔야 합니다.

**신규 알림 메일과 노출 기록 (검토 반영)**
- 메일 본문(절 나눔, 현황판 링크, 실패 소스 표시)은 `daily_report`의 새 명령이 결과 파일로 만듭니다. Apps Script는 받은 본문을 보내기만 합니다.
- 메일 발송에 성공하면 그날 메일에 실린 항목의 노출 기록을 남기고, 실행 기록에 도착 결과를 적습니다. 지금 `record-publish`가 쓰는 artifact 게시 결과의 자리를 메일 발송 결과가 대신합니다. 현황판 게시 결과는 따로 적되 도착 판정에는 쓰지 않습니다(도착 기준은 결정 대기 #3).

**추출 에이전트와 인용 대조 (H9)**
- 추출 에이전트는 첨부 텍스트를 읽어 `requirements.json`(형식: `eligibility-input.md`)과 `signals.json`(형식: `demo-brief-input.md`)을 씁니다. 판정은 하지 않습니다.
- `gov_agent eligibility`와 `gov_agent brief`에 첨부 텍스트 폴더를 받는 선택 인자를 더합니다. 인자가 있으면 각 근거 문장이 그 텍스트에 실제로 있는지 공백을 정규화해 대조하고, 없으면 그 항목을 확인필요로 내립니다. 대조는 이 두 명령 안 한 곳에서만 합니다.

**시트·메일·현황판 연결 (D19, D28~D30)**
- `apps-script/`의 웹 앱이 세 가지를 맡습니다: 행 추가·갱신(POST), 마감 전 행과 상태 읽기(GET), 메일 발송(POST). 주소와 토큰은 작업 폴더 `.env`에만 둡니다.
- 마감 지난 행 정리는 같은 Apps Script의 시간 트리거가 매일 새벽에 합니다(D29). 대표 메일 주소는 스크립트 속성에만 둡니다.
- 현황판 HTML은 `daily_report`의 새 명령이 시트 응답으로 만들고, 스킬이 Artifact 도구로 같은 주소에 다시 게시합니다. 주소는 작업 폴더의 파일 하나에 둡니다.
- 시트·메일·게시 중 하나가 실패해도 나머지 단계는 이어 가고, 실패는 실행 기록에 남깁니다.

**개발 하네스 (H10)**
- 통합 시험 실행기: 저장소의 모든 `test_*.py`를 한 명령으로 찾아 돌립니다. 지금은 gov-agent(63개)와 daily-report(54개)가 따로 돕니다.
- 결과 계약 시험: gov-agent가 고정 응답으로 만든 결과 파일을 daily-report의 입력 함수가 형식 오류 없이 읽는지 확인합니다. 두 쪽 중 하나라도 형식을 바꾸면 실패합니다.
- 가짜 응답 리허설: 임시 작업 폴더에서 고정 응답으로 daily-routine의 코드 단계 전체(수집 → 결과 파일 → 시트 동기화 → 메일 본문·현황판 HTML → 실행 기록 → 노출 기록)를 돌려 `runs/runs.jsonl`을 실제로 만듭니다. 시트·메일·게시는 가짜 클라이언트로 바꿉니다.
- 플러그인 구조 검사: `claude plugin validate --strict` 통과(사내 `proposal_agent`가 같은 옵션을 쓰고 있으나, 구축 첫날 도움말로 다시 확인합니다), `bin/` 없음, 스킬·에이전트 본문의 경로가 `${CLAUDE_PLUGIN_ROOT}`로 시작함, 스킬이 가리키는 파일이 있음, 저장소에 `.env`·`settings/`·`results/`가 없음.
- 커밋 전에 통합 시험을 돌립니다. 원격 CI는 저장소를 만든 뒤 정합니다.

## Testing Decisions

- 좋은 시험은 밖에서 보이는 동작만 확인합니다. 기존 gov-agent와 daily-report 시험의 경계(경계 A 수집, 경계 B 검토, 경계 C 보고)를 그대로 씁니다.
- 훅 시험: 설정 파일 값만 바꾼 Edit 입력은 막히고, 값과 변경 이력을 함께 바꾼 입력은 통과하며, `settings/` 밖의 파일은 검사하지 않습니다. 세션 시작 훅의 출력이 `invariants.md`와 같습니다.
- 인용 대조 시험: 원문에 있는 인용은 판정이 그대로이고, 없는 인용은 확인필요로 내려가며, 대조 인자가 없으면 지금과 같습니다.
- 스킬은 외부 도구(Artifact, Adobe, 시트)를 부르므로 자동 시험을 두지 않습니다. 가짜 응답 리허설이 코드 단계를 대신 확인하고, 스킬 본문은 플러그인 구조 검사가 파일 참조만 확인합니다.
- Cowork에서 확인할 사실은 시험 기록으로 남깁니다(아래 Further Notes).
